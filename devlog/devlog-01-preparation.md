# LinkDeck Devlog #1 — Public Preparation Brief

**Working title:** *I'm Building a Tiny NFC Device From Scratch — LinkDeck Devlog #1*

**Status:** Prepared internally; not published yet.

The first LinkDeck devlog is intended to introduce the project honestly at prototype stage and show the transition from digital preparation to real hardware validation.

This public brief describes the planned scope without publishing the complete internal script or production notes.

## Purpose

Devlog #1 should explain:

- What problem LinkDeck is trying to solve
- What the current product concept is
- Why NFC and QR are central to the sharing experience
- What hardware direction is being used for the first prototype
- How the UI/UX is being designed for a very small touchscreen
- How the project separates public development from production-sensitive engineering
- What will be physically tested next

The episode should clearly distinguish between **working hardware**, **planned behavior** and **conceptual design**.

## Core message

LinkDeck is a compact physical device for digital identity, NFC sharing and connected experiences.

The project is currently moving from digital preparation toward physical prototype validation.

## Planned structure

The current episode outline is:

1. **Hook** — why build a physical digital-identity device?
2. **The problem** — sharing different profiles, links and contact information is often fragmented
3. **The LinkDeck concept** — touch-first device, profiles, NFC and QR
4. **Prototype hardware direction** — ESP32-S3, small AMOLED touchscreen and NFC prototype
5. **Mechanical direction** — compact enclosure and real fit constraints
6. **UI/UX direction** — swipe, tap, long press and a minimal sharing flow
7. **Digital groundwork** — GitHub, documentation, branding and validation planning
8. **First hardware tests** — display, touch, NFC, QR, power, thermal and enclosure validation
9. **What comes later** — software expansion only after the core prototype is stable
10. **Build in public** — follow the real wins, failures and changes

## What can be shown before hardware arrives

Public-safe material may include:

- LinkDeck branding and Ray
- Public GitHub repositories
- Public documentation
- Approved UI wireframes/previews
- High-level mechanical visuals approved for public use
- Public roadmap and prototype milestone summaries

Concepts must be labeled as concepts rather than presented as finished hardware.

## What waits for real hardware

The strongest final version should include real footage such as:

- Development board arrival/unboxing
- AMOLED powering on
- Touch interaction
- Real NFC test with a phone
- Real QR scan from the AMOLED
- Mechanical dry fit
- USB-C programming/connection
- Power measurements
- The assembled prototype

No simulated or AI-generated render should substitute for real hardware proof once physical evidence is available.

## Technical-claim rule

A capability should only be described as **working** after it has been physically validated.

Before that, use language such as:

- planned
- target
- prototype direction
- designed to
- expected to

This applies particularly to NFC reliability, battery life, charging, performance, thermal behavior and production hardware.

## Public/private boundary

Devlog material must not expose:

- Credentials, API keys, tokens or recovery codes
- Private repository contents not approved for release
- Complete production CAD
- Complete production firmware
- Manufacturing BOMs or supplier-sensitive information
- Provisioning or security implementation details
- Personal addresses, order identifiers or account information

## Publication gate

Devlog #1 should only be considered ready to publish when:

- Technical claims match the current prototype state
- Real footage and conceptual material are clearly distinguished
- No confidential material is visible frame-by-frame
- Hardware-dependent claims are backed by real evidence
- The thumbnail accurately represents the real project state
- Links and public references are verified
- The final export has been reviewed end-to-end

## Current status

The narrative, base script, production plan, thumbnail direction and publication checklist are prepared internally.

Final recording/publication remains intentionally dependent on obtaining enough real prototype footage to make the first episode credible and useful.
